# Requirements Brief — KA2-only `system/sensord` cleanup

**Revision:** active design r4 / intake revision 89  
**Sources mined:** `intake/report_grilling.md` (SHA-256 `a51313a34983497a27a5c9ddc5cdc0c9f82d725f6c8cdf382ab2dae2c75edd4e`); `intake/intake-brief.md` (SHA-256 `c2e026d40ff71df11fd3d0277704255c51df061bbf3ffc5c7b81187513b9dc75`); current `system/sensord`, manager, loggerd, test, Jenkins, cereal schema, and shared build sources; prior r5/r6 implementation, test, and benchmark reports under this run.  
**Prepared for:** `design/architect`

This amendment supersedes the r3 requirements for KA2-only manager gating, direct-entry rejection, and a guard-only test. D-20 confirms KA2 as the deployment target, removes those platform checks, and preserves the existing KA2 runtime sequence. It does not authorize device access or settle target hardware identity or performance.

Confidence follows the researcher workflow: `observed` means read directly from a project artifact or source; `reported` means a persisted stakeholder or project decision; `inferred` means a stated conclusion from adjacent project evidence; `assumed` means no project evidence. Severity uses the shared `Critical | Major | Minor | Info` scale. A reported requirement becomes observed only after build evidence verifies the resulting artifact.

## Non-goals

- No TICI/tizi runtime compatibility in `system/sensord`; reopening requires a new approved platform-scope decision.
- No support or behavior guarantee for a non-KA2 deployment or direct invocation. D-20 removes both the manager platform gate and `sensord.main()` guard because the confirmed deployment target is KA2; behavior outside that target is unverified.
- No change to KA2 sensor topology, register setup, sampling rate, event data, calibration math, error handling, or shutdown; reopen only for an approved hardware/interface change.
- No shared log-schema migration; historical LSM/MMC enum removal requires a separate approved migration and archive-decoding plan.
- No redesign of thread or bus ownership and no approximate gyro calibration; reopen only through a separately approved, numerically checked change.
- No sensor-device test or target performance claim in the current phase. Reopen when a confirmed KA2 rig and an agreed measurement window are available.
- No changes to unrelated UI, framework, dependency, generic manager, root SCons, or release-history behavior.

## Limitations

- D-20 confirms KA2 as the deployment platform, but no board revision, sensor identity, authorized rig, or target baseline is recorded. This research made no hardware or I2C access. Offline tests and synthetic benchmarks cannot establish KA2 daemon startup, live cadence, physical accuracy, or target CPU/RSS.
- The manager's `only_onroad` predicate remains, but manager startup is no longer platform-gated and direct `sensord.main()` entry is no longer guarded. Non-KA2 behavior is outside the confirmed deployment contract and remains unverified; no non-KA2 safety or startup claim is made.
- The prior r5 offline run passed 12 cases but included LSM6DS3 and MMC5603 fixtures. The cleaned KA2-only suite and D-19 path-conditional Jenkins integration still need implementation and a fresh CI run. Under D-20, delete the r3 guard-only `system/sensord/tests/test_sensord.py` and remove the manager-gating-only assertion; do not add a replacement platform-check test.
- Historical enum names and ordinals are directly visible in `cereal/log.capnp`, but no archived log fixture was read in this research.
- Intake also reports the active local harness at Python 3.12.3 (below the 3.13 minimum) with missing Codex hooks. This is an environment readiness limitation owned by Admiral/operator, not evidence about KA2 sensord behavior.
